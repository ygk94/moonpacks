# Moonpacks mechanics: contract specification

Reference for the series mechanics implemented in `contract/` (see [`contract/README.md`](../contract/README.md)):
gold packs and pity, burn-driven rarity, gold rush, resurrection of dead coins, random value per pack, anonymous
mythics, storage refunds and treasury, and pack kinds. Heights are in blocks; durations assume 0.6 s per block.

## 0. Common principles

- **Everything is in the hashed table.** Parameters live in `SeriesTable.mechanics`, after the other table fields,
  so they are covered by `table_hash = sha256(serde_json::to_vec(table))`. **Without mechanics the field is absent
  from the JSON** (`skip_serializing_if`): an older table keeps exactly its bytes, hash and draws.
  `draw_vectors.json` regenerated by the current code is byte-identical.
- **JSON order** (locked by `hash_stream::tests::mechanics_field_order_is_locked`):
  `"mechanics":{"gold":{"slots":[{"floor","weights"|null,"burnable"}...]}|null,"pity":{"p0_ppb","k_ppb","p_max_ppb","n_max"|null}|null,"burn":{"floor_bps","prior_k"}|null,"rush":{"ratio_bps","min_packs","window_blocks","baseline_blocks","bucket_blocks","duration_blocks","cooldown_blocks","max_per_account","weights"}|null,"resurrection":{"eligible":[...]}|null,"value":{"normal":[[bps,weight]...],"gold":[...],"rush":[...],"multipliers":{...}}|null}`.
  The gold pack is described by per-slot floors (section 8); there is no separate gold weight table.
- **All state that influences a draw is frozen, then logged.** The verifier recomputes every draw from events alone
  (`pack_bought`, `pack_revealed`, `card_redeemed`, `card_resurrected`), with no state archive
  (`verifier/`, `SeriesReplay`).
- **Randomness.** A single source, `acc`. The gold decision uses tag `roll(acc, 0, 2)`, the pack value
  `roll(acc, 0, 3)`. Per-slot tags 0 (rarity) and 1 (card) are unchanged. `roll(acc, slot, tag)` is
  `u128_be(sha256(acc || slot || tag)[0..16])`.
- **The last reveal receipt has no result-dependent failure.** Pity, burns and the rate table are read and written
  in `finalize_pack` with no `require`. Added storage is bounded and prepaid (pity entry included), unused prepaid
  storage is refunded by a plain transfer after minting (section 12), and gas stays fixed (120 Tgas; about 50 Tgas
  measured in the worst case, with cascading exhausted rarities, gold pack and value). Value cannot overflow:
  validation requires `price x V_max x max_multiplier` to fit in a u128.

Default parameters (`contract/scripts/serie-exemple.json`). Base rarity weights are
5 / 40 000 / 360 000 / 1 600 000 / 17 999 995 out of 2·10⁷ (mythic / legendary / epic / rare / common), i.e. the
same visible-rarity proportions as 20 / 180 / 800 / 8 998 out of 10⁴. Mythic is 5 / 2·10⁷ per slot on the first 4
slots, the 5th being drawn among burnables, so **1 mythic per 1 000 000 normal packs**.

| Mechanic | Defaults |
|---|---|
| Gold pack | 5 cards, no common: slots 1 and 2 rare or better (slot 2 burnable), 3 and 4 epic or better (truncated base weights), 5 legendary 99 % or mythic 1 % (section 8) |
| Value | normal 20 % to 200 % of the price, mean 75 %; rush same shape, mean 75 %; gold 100 % to 800 %, mean 218.5 %; multipliers common 1, rare 2, epic 5, legendary 20 (section 9) |
| Pity | no guarantee (`n_max` = `null`); p0 = 1 / 50 000 (20 000 ppb), k = 20 ppb per pack, cap 1 / 25 000 (40 000 ppb), reached after 1 000 packs |
| Burns | floor 25 % (`floor_bps` = 2 500), prior K = 20 (`prior_k`), renormalized among the burnables of the rarity |
| Rush | relative threshold x2.5 (`ratio_bps` = 25 000), at least 100 packs, short window 6 000 blocks (1 h), long window 144 000 (24 h), buckets of 1 500 (15 min, 96 buckets), rush lasts 3 000 blocks (30 min), cooldown 36 000 (6 h), at most 3 rush packs per account per rush (`max_per_account`) |
| Resurrection | hashed list `resurrection.eligible` (rule `dead_epic_legendary` of `build_series.py`: unbacked epic and legendary "dead" coins of the catalogue); oracle change after 144 000 blocks (24 h, `oracle_delay_blocks` of `new`) |
| Rush table | mythic x1, legendary x1.51, epic x1.34, rare x1.17: 5 / 60 400 / 482 400 / 1 872 000 / 17 585 195 (mythic stays 1 per 1 000 000 rush packs) |
| Coverage (off-chain) | with a value table: mean of each table (base 75 %, gold 218.5 %, rush 75 %, rush must be at most 80 %); without: rarity values of `coverage_check` |

## 1. Minimal per-card storage

A card only stores its reference:

- `token_id = pack_id x 10 + slot`, canonical decimal (at most 10 cards per pack);
- the pack holds the series, the compact draw of each slot (`PackDraw`, 31 bytes: rolls, rarities, kind, index) and
  a 10-byte `CardSlot` (owner, `None` while the buyer holds it; state; list positions);
- NEP-181 lists (cards per account, all cards, packs per account) are stored in chunks of 32 or 64, 8 bytes per
  card; removal swaps with the last entry;
- NEP-177 metadata (`title`, `media`, `reference`, `copies`, `issued_at`, `extra`), backing and the sealed or
  revealed state of mythics are **rebuilt on read** from the table (`nft_token`, `nft_tokens`,
  `nft_tokens_for_owner`, `get_card`, `get_backing`). `issued_at` comes from the draw time stored in the pack.
  Mythic metadata is anonymous and never changes (section 11);
- `price_paid` and `storage_prepaid` in `get_pack` are derived from the series; each seed's `acc` is recomputed by
  chaining from `initial_acc`.

NEP-171, 178 and 181 are reimplemented (without `NonFungibleToken`) with the same methods, messages and approval
storage policy. `reveal_mythic` no longer rewrites sealed cards (5 Tgas instead of 85.6).

| Pack storage (sandbox) | Full per-card storage | Minimal storage |
|---|---|---|
| v2 series (5 cards), max | 3 965 bytes | 848 bytes without mechanics, 971 bytes with all mechanics, gold pack and value |
| v2 series, prepaid (`storage_per_pack`) | 15 715 bytes | 1 605 bytes |
| 4-card table | 4 235 bytes / 11 655 prepaid | 888 / 1 227 |
| 2 000 cards, 10 per pack, all mechanics | not measured | 1 266 bytes on an account's first purchase, 879 to 947 afterwards, 2 025 prepaid |

Value adds 7 bytes per pack (`Pack::value`: `bps` and the burnable mask), not 16 bytes per card: amounts are
recomputed from these bytes, the table and the drawn rarities (`draw::split_value`). Prepaid storage counts 8 more
bytes (`PACK_VALUE_BYTES`) and, if the gold pack has more slots than `cards_per_pack`, the extra cards.

A pack for an already-known account costs about 560 bytes; the first purchase adds the account counters and the pity
entry. The prepaid amount is a bound computed at opening (`worst_case_pack_storage`: 64-character accounts, new list
chunks, first purchase). The surplus is refunded by the last receipt from measured storage (section 12).

## 2. Pity counter (ultra-rare gold pack, no guarantee)

- **State**: `pity: (account, series) -> n`, consecutive packs without a gold pack, read and written by the last
  receipt. View: `get_pity(account_id, series_id)` -> `n`, `p_ppb`, `packs_to_max` (packs before the cap, 0 once
  reached), `guaranteed_in` (`null` without `n_max`), `params`.
- **Formula** (ppb, parts per billion; the slope does not fit in whole ppm):
  `p(n) = min(p_max_ppb, p0_ppb + k_ppb x n)` in u128; `gold_roll = u128_be(sha256(acc || 0x00 || 0x02)[0..16]) mod 10⁹`;
  the pack is gold if `gold_roll < p(n)`. **No guarantee by default**: `n_max` is optional; with `n_max = N`, the
  N-th pack without gold is gold (`n + 1 >= N`), which is used in tests.
- **Defaults**: `p0_ppb` = 20 000 (1 / 50 000), `p_max_ppb` = 40 000 (1 / 25 000), `k_ppb` = 20, so the cap is reached
  after (40 000 - 20 000) / 20 = **1 000 packs** (in general `k = (p_max - p0) / packs`).
- **Bounds** (validated at creation): `p0_ppb`, `k_ppb`, `p_max_ppb` <= 10⁹; `p0_ppb <= p_max_ppb`; `n_max` absent
  or 1 to 10 000; rejected if `p_max_ppb = 0` without `n_max` (unreachable gold pack). `n` is a saturating u32.
- **Pack table** (`draw::pack_mode`): pity gold pack -> gold slots (section 8) and gold value table; otherwise rush
  pack -> rush table and rush value table; otherwise base and normal value table. Pity wins over rush.
- **Update** (`draw::pity_after`): `n <- 0` **only** after a gold pack; otherwise `n <- n + 1`, rush packs included.
- **Frequency** (simulation): about 1 gold pack per 25 250 packs for a player who never stops, about 1 per 48 000 over
  a realistic population (most players open few packs).
- **Hashed**: `gold`, `pity`. **Logged**: `pack_revealed.mechanics.pity` = `before`, `gold_roll`, `p_ppb`, `gold`,
  `after`, plus `mode`. The verifier recomputes `gold_roll`, `p`, the decision and `after`, and chains each
  account's counter from pack to pack. It also reads the older ppm format of earlier testnet series.
- **Cost**: about 120 bytes on an account's first draw in the series (prepaid); one read and one write in the last
  receipt.
- **Not implemented: counter held in a tradable NFT.** It would require a special "counter" card per series, reading
  the counter from that card at draw time, logging it by `token_id`, and following transfers in the replay. With a
  tradable counter, coverage tends to the never-stopping player's value (67.5 %) and would need recalibration.

## 3. Burn-driven rarity

- **Per card**: one card is one coin. Only visible cards are affected, not mythics.
- **The rarity draw does not change.** `rarity_roll` only uses the rarity weights of the pack's table. Burns only
  affect the choice of card **within the rarity**, and fallback when a rarity is exhausted.
- **Renormalization among burnables.** For a burnable card `i` backed by the table, with weight `w`, `e` copies
  minted and `b` burned, its raw weight is 0 if exhausted by its cap, `w` if `e = 0`, and otherwise
  **`raw = max(floor(w x (e - b + K) / (e + K)), floor(w x floor_bps / 10⁴), 1)`** with `K = prior_k` (a prior:
  as if each card had `K` extra copies minted and never burned).
  **Resurrected card**: first compute `E0 = sum raw` and `B0 = sum available weights` of the **table's** burnables
  of the rarity; its raw weight is `min(own raw, max(floor(w x E0 / B0), floor(w x floor_bps / 10⁴)))` (own raw if
  `B0 = 0`). It enters at the **mean ratio** of its rarity's burnables instead of full weight, and its own burns
  still lower it.
  Then, per rarity, `E = sum raw` and `B = sum available weights` of all burnables. The in-rarity weight is
  `raw x B` for a burnable and `w x E` for a collection card (`w` if `E = 0`). The burnables' share of the rarity
  therefore stays exactly `B / (B + sum w of collection cards)`: weight lost by one burnable goes to the other
  burnables of the same rarity. The probability of drawing a burnable, and coverage, do not move. All integer math
  (u128, at most 2⁸⁶), no rounding on shares; `card_roll` is 128 bits.
- **Choice of K.** K is set, not derived, at the order of expected mints per burnable card: an epic drops about
  0.00038 times per pack, a legendary about 0.00048, i.e. 5 to 7 copies a month at 20 packs/h and 28 to 34 at
  100 packs/h. K = 20 sits in the middle. A card minted once and burned keeps 95 % of its weight (20/21); the 25 %
  floor is only reached at `e = b = 3K` = 60 burned copies. In the review scenario (10 equal-weight burnable epics,
  9 cheap ones minted once and burned), the 10th goes from 10 % to **10.5 %** of burnable epics instead of 30.8 %
  without smoothing (`early_burns_are_smoothed_by_prior`).
- **Floor**: 25 % of base weight while the card is not exhausted by its cap. A coin burned down to the last copy
  keeps the floor and never disappears (`raw_burn_weight_rounding_and_floor`). A rarity with a single burnable does
  not change: renormalization gives it back its full weight.
- **State**: `BurnState { burned[i], seq }` per series, updated in `on_redeem_complete` (successful burn of a visible
  card). Mythic burns do not count. `Series.draw_cards[i].backed` becomes true on resurrection.
- **Hashed**: `burn.floor_bps`, `burn.prior_k`, `resurrection.eligible`. **Logged**: `card_redeemed` = `series_id`,
  `kind`, `index`, `burn_seq` (burn sequence number in the series), `asset_id` and `amount` **delivered** (backing
  read by `redeem` and passed to `on_redeem_complete`), `replaced_by` (current backing if replaced during the burn,
  otherwise `null`); `card_resurrected` = `card_index`, `resurrect_seq`; `pack_revealed.mechanics` = `burn_seq`,
  `resurrect_seq` (state read at draw time). The verifier applies burns and resurrections with sequence numbers up
  to those of the draw, and reports a missing number.
- **Views**: `get_series.burned`, `get_series.burn_seq`, `get_burns` (paginated), `get_rates`: `effective_weight`
  per card and `effective_card_weight` per rarity (the modulus of `card_roll`).
- **Cost**: 4 bytes per table card for counters, paid by the owner at load time; `on_redeem_complete` at most
  3.7 Tgas (20 fixed); the last receipt makes two more passes over the rarity's cards.

## 4. Collective gold rush

A fixed threshold runs away (in simulation, 69 % of packs became gold at x2 traffic). The threshold is therefore
**relative to the last 24 hours of traffic**, with a **cooldown** between rushes and a **dedicated rush table**.

- **Sliding window at bounded cost**: `m_l = baseline_blocks / bucket_blocks` buckets (at most 96, a ring in the
  series), `m_w = window_blocks / bucket_blocks`. The bucket of height `h` is `floor(h / B)`. A purchase increments
  its bucket; `C_w` and `C_l` count purchases in the last `m_w` and `m_l` buckets, current one included.
- **Rush pack**: a trigger happened at `t`, `t < h <= t + duration_blocks`, **and** the buyer bought fewer than
  `max_per_account` rush packs during this rush (state `(account, series) -> (t, n)`, reset at each trigger,
  `draw::rush_account`). Beyond the cap, the pack is normal. **The state is frozen at purchase** (`buy_pack`, flag
  `FLAG_RUSH`); delaying the reveal changes nothing.
- **Trigger** at purchase height `h` when all hold:
  - no rush or cooldown in progress: `h > t + duration + cooldown`, or no trigger yet;
  - the long window is filled: `h >= first purchase of the series + baseline_blocks`;
  - `C_w >= min_packs` (absolute threshold) **and** `C_w x m_l x 10⁴ >= ratio_bps x C_l x m_w` (relative threshold):
    at least `min_packs` packs in the hour and a short-window rate at least `ratio` times the 24 h average.

  The triggering purchase is not itself a rush pack. Purchases during the rush count in the windows.
- **Validation at creation**: `ratio_bps >= 10⁴`, `ratio_bps x m_w < 10⁴ x m_l` (otherwise unreachable), windows
  multiples of the bucket, `m_w < m_l <= 96`, duration >= 1, `min_packs >= 1`, `max_per_account >= 1`, valid rush
  table.
- **Rush triggered by a single actor.** Measured with the same rules as the contract: 30 h of steady background
  traffic, then one actor buys 50 packs in one block and 200 more, one per block. Gain = expected gain over a base
  pack, `0.799 - 0.587 = 0.212` price per rush pack.

  | Background traffic | Without cap (min 50) | With cap (min 100, 3 per account) |
  |---|---|---|
  | 0 / h | minimum burst 50; 200 rush packs out of 200, gain 42.4 prices | minimum burst 100; 3 rush packs, gain 0.64 price |
  | 20 / h | minimum burst 35; 200 rush packs, gain 42.4 prices | minimum burst 81; 3 rush packs, gain 0.64 price |
  | 100 / h | minimum burst 169; 59 rush packs, gain 12.5 prices | minimum burst 169; 3 rush packs, gain 0.64 price |

  **Maximum gain per actor**: `max_per_account x 0.212 = 0.64` pack price per account per rush, at most one rush
  every `duration + cooldown` = 39 000 blocks (6.5 h). Triggering costs at least `min_packs` base packs (expected
  loss 41.3 % of the price each, about 41 prices for 100 packs): a single account loses. With `A` accounts (Sybil)
  the gain is `0.64 x A`: about 65 accounts are needed to cover the burst, before first-purchase storage. A rush
  pack still has negative expectation (79.9 % of the price).
- **Random delay before the rush: not used.** A few blocks of delay drawn from a receipt seed would not stop the
  actor, who simply buys after the delay (the rush lasts 3 000 blocks), and the receipt seed is not recomputable by
  the verifier, which would break replay from events.
- **Coverage <= 80 %, checked off-chain.** The contract does not know card values (a backing is a token quantity,
  not a price). `scripts/build_series.py` computes each table's coverage and **rejects** a rush table above
  `max_rush` (0.80); `scripts/validate_series.py` checks the mean of value tables.
- **Hashed**: the whole `rush` block (table and cap included). **Logged**: `pack_bought.rush` = `active`,
  `window_count`, `baseline_count`, `triggered`, `last_trigger`, `rush_until`, `rush` (rush pack), `capped`,
  `account_rush_packs`; `pack_revealed.mechanics.rush`. The verifier replays the ring and per-account caps from
  `pack_bought` events; a missing `pack_bought` for a rush series is an error. View:
  `get_rush_state(series_id, at_height, account_id)` (`account.rush_packs`, `account.remaining`).
- **Cost**: ring of 96 x 12 bytes in the series, paid by the owner; `buy_pack` reads 96 buckets and writes one
  (+1 Tgas); per-account cap entry (130 bytes prepaid, `RUSH_ENTRY_BYTES`).

## 5. Resurrection of dead coins

- **Abstract `price_oracle` role**, like the redeemer. **Two-step change**: `propose_price_oracle(Option<AccountId>)`
  (owner, event `price_oracle_proposed` with `effective_from`), then `accept_price_oracle()` (owner, no earlier than
  `oracle_delay_blocks` after the proposal, event `price_oracle_accepted`). The delay is a `new` parameter
  (144 000 blocks = 24 h by default); a new proposal replaces the previous one and restarts the delay.
  `revoke_price_oracle()` (owner) removes the oracle immediately (event `price_oracle_revoked`): removing can only
  prevent resurrections. View `get_config`: `price_oracle_id`, `price_oracle_pending`, `oracle_delay_blocks`.
  `set_resurrected(series_id, card_index, backing)`: oracle only, payable (measured storage, excess refunded).
- **Scope**: **the cards in `mechanics.resurrection.eligible`**, a list committed in the hashed table (strictly
  increasing indexes, at most 200). Each index must be a visible **epic or legendary card not backed** by the table
  (checked at opening; rare and common rejected, since in simulation 94 % of the cost would come from commons).
  Without this field, no resurrection. A new call replaces the backing of a listed card.
- **Effect**: the card becomes burnable for new copies **and** existing ones, since backing is read on demand
  (`get_backing`, `redeem`, `extra.burnable` in metadata). It joins its rarity's burnables for burn renormalization
  (`resurrect_seq`) at the mean ratio (section 3), not at full weight.
- **Event** `card_resurrected`: `series_id`, `card_index`, `card_id`, `backing`, `previous`, `oracle_id`,
  `resurrect_seq`, `block_height`. No `nft_metadata_update` (it would require listing every copy).
- **Mock**: `contract/mock-oracle/` (`push_resurrection`, operator only) calls `set_resurrected`. No price is read.
- **A production oracle would need**: a manipulation-resistant price source (several sources, median, multi-hour
  TWAP, since micro-caps are easy to move); a published per-coin threshold rule with a minimum duration above it;
  actual purchase of the token inventory **before** the call, since the backing is a delivery promise to the
  redeemer; a dedicated fund; and governance of the oracle account (multisig, delay). The contract checks neither
  price nor inventory: it trusts the oracle, as it trusts the redeemer.
- **Cost**: about 150 bytes per resurrected card (paid by the oracle), one rewrite of the series.

## 8. Gold pack: per-slot rarity floor

The pity counter decides when a pack is gold; the gold pack itself is a list of slots, each with a **rarity floor**.

- **Table**: `mechanics.gold.slots`, 1 to 10 slots (independent of `cards_per_pack`; prepaid storage uses the larger
  of the two). Each slot has `floor`, `weights` (own weights, zero below the floor) or `null` (base weights zeroed
  below the floor, `draw::gold_slot_weights`), and `burnable` (drawn among burnables).
- **Default**: 5 cards, no common. Slots 1 and 2 rare or better, 3 and 4 epic or better (truncated base weights: the
  proportion between rarities above the floor is the base one), slot 5 legendary 99 % or mythic 1 %
  (`weights` = 1 / 99). Slot 2 is `burnable`: it carries the pack value.
- **Draw**: `rarity_roll = roll(acc, slot, 0) mod sum of the slot's weights` (same tag), target rarity by cumulative
  sum.
- **Exhausted rarity** (`draw::fallback_order`): the target, then **down to the floor**, then **up** (above the
  target, up to mythic), then **below the floor** down to common as a last resort. Examples: slot 5 targeting an
  exhausted legendary -> mythic; legendary and mythic exhausted -> epic; mythic at its cap -> legendary. The floor
  is only crossed when nothing is drawable above it.
- **Card choice**: as usual (`card_roll = roll(acc, slot, 1) mod sum`, burn weights included), restricted to
  burnables for a `burnable` slot.
- **Validation**: 1 to 10 slots; slot weights not all zero, zero below the floor, mythic weight only with a weighted
  commitment; a rarity weighted by a slot must have a card; `pity` requires `gold`. The rush table keeps its own
  boosted weights.
- **Hashed**: `gold`. **Logged**: `pack_revealed.mechanics.mode = "gold"` and the draws (one per slot). The verifier
  recomputes each slot (`core.draw_slot_rule`).

## 9. Random token value per pack

A pack's token value ranges from 20 % to 200 % of its price, with a mean around 75 %.

- **Tables** (`mechanics.value`, hashed): `normal`, `gold`, `rush`, each with 1 to 32 tiers `(value in basis points
  of the price, weight)`, non-zero weights; `multipliers` per rarity (mythic 0, others 1 to 10⁶). **Normal table:
  2 000 <= value <= 20 000 bps.** Gold and rush tables: 1 to 10⁶ bps. Price bounded so that
  `floor(price x V / 10⁴) x multiplier` fits in a u128.
- **Drawing V** (last receipt): `value_roll = u128_be(sha256(acc || 0x00 || 0x03)[0..16]) mod sum of weights`, tier by
  cumulative sum in table order (`draw::value_tier`). Gold table for a gold pack, rush for a rush pack (frozen at
  purchase), normal otherwise.
- **Split** (`draw::split_value`): `total = floor(price x V / 10⁴)` yoctoNEAR of value, split among the **pack's
  burnables** (visible cards backed by the table or resurrected **at draw time**) in proportion to their rarity
  multiplier: `floor(total x m_i / sum m)`, rounded down; **the remainder goes to the card with the highest
  multiplier, the first in slot order on ties**. No yocto is lost.
- **Guaranteed burnable**: the last slot of a normal pack (base or rush) is drawn among burnables. Its target rarity
  follows the normal draw (`rarity_roll` unchanged), falling back down among burnables, then up if no lower rarity
  has one (`fallback_order(target, common)`). A gold pack has its `burnable` slot (slot 2 by default) under the
  section 8 rule. A mythic is never a burnable here: its backing is in its content, secret until reveal.
- **Validation**: with a value table or a `burnable` gold slot, there must be a card **backed by the table, uncapped
  and with non-zero weight**. Since fallback walks all visible rarities, the slot always finds a burnable.
- **Backing passed on**: `redeem` sends `(asset_id, amount)` to the redeemer, with the card's `asset_id` (table or
  oracle) and **`amount` = that copy's share of the pack value**. `get_backing`, `get_card` and `card_redeemed`
  report this amount. The redeemer receives yoctoNEAR of value, not tokens; conversion depends on funding. In a
  value-table series, the table `amount` is no longer read for drawn burnable copies.
- **Fixed-backing special cases**: a **mythic** keeps the backing of its revealed content; a copy that **became
  burnable after its draw** (resurrection) has no value share and keeps the oracle amount. Copies drawn after the
  resurrection get a share.
- **Storage**: `Pack::value` = `bps` (4 bytes) and the burnable mask (2 bytes), 7 bytes with the option; amounts
  are recomputed on read. Prepaid: `PACK_VALUE_BYTES` = 8 bytes.
- **No result-dependent failure in the last receipt**: no `require`; overflows are excluded at creation; with no
  burnable (impossible for a validated table), nothing is split.
- **Hashed**: `value`. **Logged**: `pack_revealed.mechanics.value` = `roll`, `tier`, `bps`, `total`, `amounts` (per
  slot, `null` for non-burnables), and `resurrect_seq`. The verifier recomputes V, the total, the split bit for bit,
  and the guaranteed burnable (replaying `card_resurrected`).
- **Default tables** (`serie-exemple.json`; `build_series.py --tables-valeur` can replace them): normal
  `[[2000,15],[3000,13],[4000,10],[5000,10],[6000,10],[8000,10],[10000,10],[12000,8],[15000,5],[20000,9]]` (exact mean
  75 %), rush identical, gold `[[10000,30],[15000,25],[20000,20],[30000,13],[50000,8],[80000,4]]` (218.5 %),
  multipliers common 1, rare 2, epic 5, legendary 20. `build_series.py` checks the contract bounds and rejects a
  rush table with a mean above 80 % (`coverage_check.max_rush`).

## 10. Known limits

- The pity counter is tied to the account (no tradable counter, section 2).
- `prior_k` and `min_packs` are set parameters, not fitted. The per-account rush cap does not resist a
  many-account actor (section 4).
- The price oracle and the redeemer are trusted, and token sourcing for backings is outside the contract
  (section 5).
- Coverage is not checked on-chain; rarity values for `coverage_check` must be recalibrated per series.
- Durations assume 0.6 s per block.
- No `nft_metadata_update` is emitted for copies of a resurrected card, nor on mythic reveal (mythic metadata never
  changes).
- `withdraw_revenue` does not reserve backings that are not in NEAR (fixed table backings, mythics) (section 12.4);
  the 1 NEAR minimum reserve is a testnet value.

## 11. Anonymous mythics

Mythics carry no public information, before or after reveal.

- **NEP-177 metadata** (`nft_token`, `nft_tokens`, `nft_tokens_for_owner`): title `?`, description `?`, image `?`
  (`MYTHIC_MEDIA`, an SVG `data:` URI, the same for all), no `reference`, `copies` or `updated_at`;
  `extra` = `series_id`, `rarity: "mythic"`, `pack_id`. No `card_id`, commitment, mythic index or `burnable`. All
  mythics are indistinguishable in their metadata, which does not change on reveal (no `nft_metadata_update`).
- **`get_card`** for a mythic: `card_id` and `backing` are always `null`; `sealed` only says whether the commitment
  has been opened.
- **What stays public, by construction**:
  - a copy's mythic index (`pack_revealed.draws[].index`, `get_pack`, `get_card.index`, `mythic_drawn`) and the
    matching commitment (`get_mythic_commitments`, `get_rates`): required to verify the draw;
  - on reveal (`reveal_mythic`), `mythic_revealed` and `get_mythic_commitments[j].revealed` publish `card_id`, salt
    and content (title, media, backing) with the list of sealed copies: this is what makes the commitment
    verifiable, and combined with the index it links each copy to its coin. **Not revealing** keeps the secret, but
    an unrevealed mythic **cannot be burned** (its backing is in the content);
  - after reveal, `get_backing` and `card_redeemed` expose the backed asset;
  - the `media` of the committed content is built by `build_series.py` from the real mythic id; it only appears at
    reveal, never in displayed metadata.

## 12. Storage refunds, stuck-pack refund, revenue withdrawal, error codes (v3)

These changes altered the Borsh layout (`Pack::storage_used`, four counters in the root state, `refunded` status), so
v3 required a new account.

### 12.1 Prepaid storage refunded at reveal

- `buy_pack` still requires the worst case (`required_deposit` = price + `storage_per_pack` x 10¹⁹), since real
  storage is only known at draw time.
- **Metering.** Each pack receipt (`buy_pack`, each `reveal_step`, the final draw) flushes pending state
  (`flush_all`) and reads `env::storage_usage()` before and after. The difference is charged to the pack
  (`Pack::storage_used`, cumulative, view `get_pack.storage_used`). It is exact: in sandbox, `used_bytes` equals the
  change in the contract's `storage_usage` over the transaction.
- **Refund.** The last receipt refunds `max(0, storage_per_pack - storage_used) x 10¹⁹` to the buyer by a transfer.
  The contract never refunds more than what is unoccupied. Beyond the prepaid amount (retry seeds, about 90 bytes
  per retry), the contract pays.
- **Log.** `pack_revealed.storage = { "prepaid_bytes", "used_bytes", "refund" }`. The verifier checks
  `refund = max(0, prepaid - used) x 10¹⁹` (`verify.verify_storage`).
- **Why this is not a result-dependent path.** The amount depends on the draw (sealed cards, longer gold pack, first
  purchase), but there is no `require` and no call that can fail: an outgoing transfer of an amount already in the
  balance. The only conceivable failure would be `LackBalanceForState` if the balance fell below occupied storage;
  `withdraw_revenue` excludes it by keeping commitments of unrevealed packs and a reserve (12.4).

### 12.2 Storage refunded on burn

- On success, `on_redeem_complete` measures the bytes freed by the burn (NEP-181 entries of the owner and global
  lists, emptied chunks and counters, approvals, slot owner reset to `None`) and refunds them to the owner, never
  more. `card_redeemed` adds `freed_bytes` and `storage_refund`.
- **The pack slot is not freed.** `CardSlot` (10 bytes) and `PackDraw` (31 bytes) of the burned card stay because
  `token_id = pack x 10 + slot` (removing one would shift the others), the value share of the pack's other
  burnables is recomputed from the rarities of **all** slots, and `get_pack` (the web app's "Verify this pack"
  page) returns every draw.
- Measured: 16 bytes refunded for an ordinary burn (two 8-byte entries), more than 100 bytes when the burn empties
  the account's list, plus approvals.

### 12.3 Stuck-pack refund

- `refund_stuck_pack(pack_id)`: open to anyone, the money always goes to the buyer. Requires status `stuck` and no
  card written. Refunds the price and unused prepaid storage, moves the pack to `refunded`, removes the price from
  `revenue`. Event `pack_refunded` (`price`, `storage_refund`, `total`, `storage_used`, `by`).
- **A third party can neither exhaust a pack's attempts nor push it toward a refund**: `retry_reveal` is reserved
  to the pack buyer (`E_NOT_PACK_OWNER`), only after `retry_delay_blocks` (at least 20) without progress.
- **No double refund**: `refunded` is final (`E_ALREADY_REFUNDED`). **No draw afterwards**: `reveal_step` ignores
  any pack that is not `pending`, and `retry_reveal` requires `pending`.
- **No free draw, by construction.** A pack only becomes `stuck` after `MAX_ATTEMPTS` (10) failed last receipts with
  no card written; a `revealed` pack never changes state again. Seeing a bad draw and then getting a refund would
  require making the last receipt fail depending on its result, and that receipt has no such path (fixed gas,
  prepaid storage, no `require` on cards, value or counters, storage refund always covered). Tested by
  `revealed_pack_cannot_be_refunded`, `revealed_pack_can_never_become_stuck` and the sandbox test
  `stuck_pack_is_refunded_once` (10 real failed attempts).

### 12.4 Revenue withdrawal

- `withdraw_revenue(amount?)`: owner, 1 yoctoNEAR. Withdraws `amount` (everything withdrawable if omitted) to the
  owner. View `get_treasury()`. Event `revenue_withdrawn` (`amount`, `to`, `balance_before`, `committed`,
  `withdrawable_before`, `withdrawn_total`, `revenue`).
- `withdrawable = balance - commitments`, with
  `commitments = storage_usage x 10¹⁹ + listing_deposits + pack_escrow + value_reserved + 1 NEAR`:
  - occupied storage: all state, whoever paid for it;
  - `listing_deposits`: deposits of active listings, owed to sellers;
  - `pack_escrow`: `pending` and `stuck` packs, price and full prepaid storage (already-written storage is counted
    twice, deliberately, to avoid rereading the series at each step);
  - `value_reserved`: value shares (yoctoNEAR) of live burnable cards in value-table series; increases at draw by
    the sum of shares, decreases at burn by the card's share;
  - `TREASURY_MIN_RESERVE` = 1 NEAR: contract-paid storage (retry seeds, list entries of market buyers and transfer
    recipients) and a margin for refunds.
- The rest is revenue plus surplus (contract gas rewards, incoming transfers). One yocto beyond the limit is rejected
  (`E_WITHDRAW_LIMIT`); after a maximal withdrawal, a pending pack still reveals with its refund, a new purchase
  goes through, and a listing can be withdrawn with its deposit.
- **Not covered**: fixed backings of a table without value (`asset_id`, `amount` in token units) and mythic backings
  are not in NEAR; the contract cannot price them and does not reserve them.

### 12.5 Marketplace: bounded price

`list` rejects a price above `MAX_LISTING_PRICE` = 10⁹ NEAR (`E_PRICE_TOO_HIGH`): beyond it, `price x bps` of the
royalties overflowed. `compute_payout` (`nft_payout`, `nft_transfer_payout`) also rejects an amount above
`u128::MAX / 10⁴` (`E_AMOUNT_TOO_LARGE`) instead of panicking without a code.

### 12.6 Error codes

Every `require!` and panic starts with a stable `E_...: ` code followed by the message. The full list is in
[`contract/ERRORS.md`](../contract/ERRORS.md). The test
`tests_v3::every_error_has_a_stable_code_listed_in_errors_md` fails if a message has no code or the list is out of
date.

## 13. Pack kinds: themed packs within the same series (v4)

A themed pack (Dog, Cat, Solana, OG...) is not a separate series: it is a **pack kind** of the series,
`SeriesTable.kinds[i]` (`PackKind`). It draws from the **same table**, with the **same `minted` counters** and caps
as the base pack. A theme reprints nothing: a card drawn in a Dog pack counts toward its cap across the whole series,
and the rarity of a base-pack card is not diluted.

**Fields** (in this order, hashed with the table; `kinds` is absent from the JSON when `None`, so a table without
kinds keeps its bytes and hash): `name` (1 to 32 bytes, unique), `price` (yoctoNEAR), `cards_per_pack` (1 to 10),
`pool` (drawable card indexes, strictly increasing; empty = all), `mythics` (whether mythics can drop), `slots` (one
rule per card, or `null`), `value` (apply the series value table to this kind). The field is named `pool`, not
`cards`, because the pattern `"cards":[` must stay unique in the header (batched hashing, `hash_stream`).

**Purchase.** `buy_pack(series_id, kind)`: `kind` absent = base pack. Deposit: kind price + series worst-case
storage (which covers the largest kind). `pack_bought` and `pack_revealed` carry `kind` only for kind packs: a
base-pack event keeps exactly its previous shape.

**Drawing a kind pack** (`draw::draw_pack_mech` with `kind`):

- cards outside the `pool` get weight 0 (`draw::kind_cards`); mythics excluded if `mythics` is false (mythic rarity
  weight 0 and no drawable mythic);
- never a gold pack, no pity: the account's pity counter does not move; rush table if the pack is a rush pack;
- the kind's `cards_per_pack`; card `i` follows `slots[i]` if present: floor, own weights (or the pack's weights
  truncated below the floor), burnable-only draw (`draw_slot_rule`, like a gold slot); without `slots`, the default
  rule, including the guaranteed burnable last if `value`;
- value: series table, `floor(kind price x V / 10⁴)`, only if `value`; otherwise a drawn burnable keeps the table
  backing.

**Examples.** "1 Dog pack in 3 has a burnable": `value: false`, no `slots`, weights of the pool's burnables tuned to
4.9 % per card (8 cards). "At least one rare": `slots` with a `rare` floor on one card.

**Validation.** Header: number of kinds (at most 16), name, price, size, increasing `pool`, one rule per card,
nothing below the floor, value table present if `value`, no u128 overflow. At opening: `pool` indexes exist, an
uncapped common with non-zero weight in the `pool`, and an uncapped burnable if the kind guarantees one. Errors
`E_KINDS` (owner) and `E_UNKNOWN_KIND` (purchase).

**Views.** `get_series` lists the kinds (`kinds`, with required deposit and card count); `get_pack` returns `kind`
and the kind price paid; `get_kind_rates(series_id, kind, from_index, limit)` returns a kind's rates (same fields as
`get_rates`, `pool` cards only, `kind.slots` for per-card rules).

**Verification.** The Python verifier (`core.kind_table`) and the web app's verifier (`kindTable`) draw in the kind's
view of the table; their agreement with Rust is tested on 150 random tables
(`verifier/tests/vectors/kind_vectors.json`, generated by `vectorgen`). The hash is always computed on the original
table.

**Deployment.** `Pack` and `SeriesTable` each gain a field (`kind`, `kinds`), so the Borsh state changes: v4 is a new
contract (`app4.simpletea5483.testnet`), not an in-place upgrade of v3.
